# eval/scripts: specification

Deterministic parts of the eval in `eval/protocol.md`. TypeScript run with Bun: `bun eval/scripts/eval.ts <command> [args]`. Tests: `bun test eval/scripts`. Import the linter from `../../packages/core/src/index.ts`. No network, no model calls: models are dispatched by the session; these scripts prepare their inputs and score their outputs. Every command is deterministic given `--seed` (default 1).

## Files and formats

**Task file** (`eval/tasks|holdout|report-only/<id>.md`): YAML front matter as in `eval/tasks/TEMPLATE.md`, then `## Brief`, `## Facts` (lines `F<n>: claim (source: ...)`), `## Unknown`, `## Existing copy`. Parse the front matter with a small YAML subset parser or `Bun.YAML` if available; fields: id, project, set, channel, locale, audience, register, email_type?, deliverables[{name, max_chars?, min_chars?, max_words?, min_words?}], placeholders[], target_query, replaces, samples.

**Run folder** `eval/runs/<run>/`:
- `run.json`: `{ "run", "arms": ["A","B"], "n": 4, "tasks": ["<id>", ...], "samples": {"A": false, "B": true} }`.
- Generator outputs: `out/<arm>/<task>/<n>.md`, n = 1..N. Format: one `## <deliverable name>` section per deliverable, in any order, then optional `## needs`, `## decisions`, `## flags` sections (ignored for scoring). Text inside a section is the deliverable, trimmed.

## Commands

1. `units <run>` writes `units.jsonl`: `{arm, task, n, unit, text}` for every output. A deliverable with `max_chars` or `min_chars` (titles, metas, subjects, UI strings) is one unit, id `<deliverable>`. Other deliverables are split into sentences, ids `<deliverable>#1..k`. Sentence split: after `.`, `!`, `?` or `…` (optionally followed by a closing quote or bracket) when followed by whitespace and an uppercase letter, a digit, an opening quote or the end; and at blank lines and list items (`- `, `* `, `1. `). Do not split inside `{placeholders}` or `{{placeholders}}` (including punctuation, blank lines and list markers inside the token), decimal numbers (`7,5`, `7.5`), `e.g.`, `bijv.`, `o.a.`, `z.B.`, `ca.`, `incl.`, `nr.`, `St.`. Markdown headings in prose are their own unit.

2. `read-bundles <run>` writes, per task, `read/<task>.md` and `keys/<task>.read.map.json`. The bundle shows the task's locale, audience and register line, the voice samples for the task's project (only when the task front matter `samples` is not `none` and at least one arm enables samples; readers see samples in BOTH arms: include `eval/samples/<project>/judge.md` if it exists and its status is approved or the run sets `"pendingSamples": true`), then every output of that task from both arms, shuffled with the seed and labelled `X1..X(2N)`, each unit on its own line as `[X3 body#2] text`. The map file maps labels to `{arm, n}`. No arm names, file paths or counts per arm appear in the bundle.

3. `read-score <run> <readerA.jsonl> <readerB.jsonl>`: each reader file has one JSON object per flagged unit: `{"task","label","unit","quote","reason","fix"}`; unflagged units are absent. Validate: unknown task, label or unit is an error; `quote` must match the start of the unit text after normalising case, quotes (curly to straight), dashes and whitespace (compare the first 30 characters of quote, or all of it if shorter). If more than 5% of a reader's lines fail validation, exit 1 naming the reader and the failures. Output `read-score.json` and print a table: per task and arm, units, flags by reader A, by reader B, agreed (both flagged the same unit of the same output), share agreed = agreed ÷ units (per task: mean over that arm's outputs). Also the per-task difference A minus B.

4. `judge-bundles <run>`: pairs output n of arm A with output n of arm B for each task. Two bundles per task, `judge/<task>.order1.md` (A as "Copy 1" in odd pairs, "Copy 2" in even pairs, determined by the seed) and `.order2.md` (every pair's sides swapped). Each bundle shows the task's locale, audience and register line, the judge's voice samples (`eval/samples/<project>/judge.md`, same inclusion rule as read-bundles) and the brief, then pairs `P1..PN` with their two copies. Map files `keys/<task>.order1.map.json` and `keys/<task>.order2.map.json` record which side is which arm.

5. `judge-score <run> <judgeX.order1.jsonl> <judgeX.order2.jsonl> [<judgeY...> ...]`: each line `{"task","pair","prefer":1|2|"tie","reason"}`. Per judge, pair and order: B preferred = 1, A preferred = 0, tie = 0.5; average the two orders (so an order flip becomes 0.5). Task score = mean over judges and pairs, minus 0.5. Output `judge-score.json` and a table per task.

6. `guards <run>`: per output.
   - Hard: every deliverable section present and non-empty; inside its budgets (characters counted as Unicode code points after trim; words = whitespace-separated tokens); every listed placeholder present unchanged at least once; no `{...}` or `{{...}}` token that is not in the task's placeholders (double braces form one token; a single-brace substring inside double braces does not count as present); no number missing from the task's Facts section (use `createLinter(...).lint(text, { locale, facts })` from core and keep only the number rule's errors).
   - Noisy: lint errors per output (`lint(text, { locale, kind })` with kind `title` or `meta` for deliverables named title/meta, `body` otherwise), excluding the number rule.
   - Copy check (reported): the longest run of words (lowercased, punctuation stripped) shared with any text in `eval/samples/<project>/generator.md`; flag runs of 6 or more.
   Output `guards.json` and a table: per task and arm, hard failures (list), lint errors, longest shared run.

7. `report <run>`: reads read-score, judge-score, guards and factcheck-score (whichever exist; missing or incomplete dev evidence prevents keep) and writes `results.md`:
   - Preference: mean task score, sd, n tasks, and the one-sided 95% lower bound `mean - t(0.95, n-1) * sd / sqrt(n)` (hard-code the t quantiles for df 1..40).
   - Defects (reported only; they trigger nothing since the owner check failed): mean per-task difference A minus B with its one-sided 95% lower and upper bounds.
   - Hard guards: count of failing outputs per arm; any failure in B is listed.
   - Noisy guards: lint errors and unsupported-claim counts per output, mean per task and arm, difference B minus A with its one-sided 95% t interval across dev tasks. Revert if either lower bound is above zero. Fact-check evidence requires exactly one entry for every generation of both arms of every dev task.
   - Outcome per protocol section 6: a run without `pool` gives revert or "second batch needed", never keep. A run with `pool` (run.json: the sibling run folder of batch 1) pools per-task preference with batch 1's judge-score.json and gives keep, revert or inconclusive, with the reason in one line. Also report words ÷ budget per deliverable (mean per arm).
   Only dev tasks count; holdout and report tasks are listed separately and never change the outcome.

8. `owner-sheet <run>`: from read-score of an A/A run, picks 8 units both readers flagged and 7 units neither flagged, nl tasks only, seeded random, shuffled; writes `owner-check.md` (numbered items: the unit text and one line of context: the task's channel and audience; a line `answer: natural / off` to fill in, no reader reasons shown) and `keys/owner-check.key.json`. `owner-score <run> <owner-check.md>` reads the filled answers and prints matches, and confirmed agreed flags out of 8.

9. `calib-bundles`: from `eval/calibration/clean.jsonl` and `seeded.jsonl`, writes two shuffled bundles per language group (nl incl. nl-owner, en, en-dev) to `eval/calibration/read/<group>-1.md` and `<group>-2.md`, each with labels `C1..Ck`, each passage as one unit `[C4 p] text`. Maps are `eval/calibration/keys/<group>-1.map.json` and `<group>-2.map.json`. Seeded rows identify their clean twin by `clean_id`, or their own `id` when both sources use matching IDs. Missing twins or mismatched groups are errors. Shuffle clean passages and distribute alternately; place each seeded twin in the other bundle, then shuffle within each bundle. Remove obsolete combined bundles and their maps. `calib-score <readerA.jsonl> <readerB.jsonl>`: each reader file concatenates that reader's lines for all six bundles. Reader `task` identifies the bundle (`nl-1`, `nl-2`, etc.), `unit` is `p`. Scores still aggregate per group and per reader, and for agreed flags: false-alarm rate on clean passages (flags ÷ clean passages), recall on seeded passages (flagged ÷ seeded), and the protocol's pass or fail (agreed false alarms at most 15%, agreed recall at least 0.7), plus the share of nl-owner passages flagged.

10. `factcheck-bundles <run>`: writes `factcheck/<task>.md` with locale, audience, register, brief, parsed Facts claim text and Unknown. All outputs from both arms are shuffled with the seed, labelled `F1..F(2N)`, with each deliverable shown under its name. Generator notes are omitted. `keys/<task>.factcheck.map.json` maps labels to `{arm, n}`. No arm names or paths are added to bundles.

11. `factcheck-score <run> <file.jsonl>`: one line per output, `{"task","label","unsupported":["claim", ...]}`. An empty array explicitly records zero unsupported claims. Reject unknown tasks/labels, duplicate or missing rows, and arrays containing anything other than non-empty strings. No reader validation tolerance applies. Write `factcheck-score.json` as `{outputs: [{task, arm, n, unsupported}]}` and print per-output unsupported-claim counts. Report computes mean counts per task and arm, then the B minus A interval across dev tasks.

All label and owner answer maps live in `keys/`, outside reader bundle folders. Regeneration removes the corresponding old map beside its bundle. Scoring reads only the new paths. Distribute only blind bundle Markdown files to readers, never keys or score files.

## Tests

Fixtures under `eval/scripts/__tests__/fixtures/` (two small tasks, a run with N=2, reader and judge files). Content-bearing assertions: sentence splitting on the listed cases (abbreviations, decimals, placeholders, list items); bundles contain no arm names and every unit once; quote validation and the 5% rule; agreement counts; order-flip averaging gives 0.5; t lower bound against a hand-computed value; every hard guard fires on a crafted bad output and stays silent on a good one; owner sheet has 8 + 7 items with no reasons shown; seeded determinism (same seed, same bundle). Load every real task from all three task directories except TEMPLATE.md. Check exact double-brace presence/missing/unknown behavior, samples:none with project samples, label key locations, fact-check bundle contents and score counts, noisy-guard intervals and missing evidence, and twin separation across all calibration bundles. Pairing tests use distinct output content so a duplicated or mismatched pair fails.
